# 项目连续性要求与验收

本文件保存 2026-10-12 用户请求的完整可执行范围、限制和验收方式；实际进度只维护在
[STATUS.md](STATUS.md)。长期工作规则见 [../AGENTS.md](../AGENTS.md)。

## 目标与范围

采用“AGENTS.md 长期规则 + Markdown 当前状态与必要计划 + GitHub 云端里程碑提交”。
目标仓库固定为 `https://github.com/EndiVee233/SubFabric`；使用可用连接器、GitHub API 或
已认证的 `gh api` 直接创建云端提交，不初始化本地仓库，不执行本地暂存、提交或推送。

这是对已有任务的补充，不替代、不缩减已有明确的开发需求。完成基础配置后立即继续已有任务，
不等待再次确认；如果会话只要求连续性配置，则完成配置、验证和可执行的云端提交，不扩展业务工作。
仅对当前任务中明确归属且经过核对的改动授权直接创建里程碑提交，无需逐次询问。

2026-10-12 后续授权补充：当前账号不能直接写入上游时，用户明确要求提交 PR。
允许使用已有 `R2FtYml0/SubFabric` fork，从最新上游基线创建独立文档分支，通过云端 API 保存本次增量，
并向 `EndiVee233/SubFabric` 的目标分支发起 PR；不创建新仓库、不修改 fork 默认分支、不夹带其他提交、
不自动合并。分别核对 fork 提交、上游 PR 和合并状态；创建 PR 不等于已进入上游默认分支。

## 检查与基线

1. 先确认实际源码根目录及与目标仓库的对应关系，再有针对性检查相关 AGENTS、README、
   STATUS、PLAN、roadmap、TODO、ADR/DECISIONS、需求/验收、代码、配置、启动与测试入口。
2. 首次配置建立必要项目认识；后续复用状态与已有资料，只核对相关变化。
3. 检查目标分支、相关远程文件和少量近期提交。优先沿用分支约定；没有约定时读取默认分支，
   不假定叫 main/master。核对仓库身份、访问权限、保护要求和已有检查。
4. 轻量记录开始时的相关文件内容/哈希、已有差异与远程 HEAD；区分用户原内容、本次修改与远程并发变化。
   不复制整个项目、不移动用户文件、不改变既有本地版本管理状态。
5. 保留用户所有已有文件和修改。不递归读取依赖、模型、运行时、构建产物或大量无关文件，
   不完整输出大型日志和全部历史。根目录、关键需求或仓库关系确实不明时指出缺失信息，
   暂停远程写入并继续安全的检查和文档工作，不编造状态或实现范围。

## 文档职责

- **AGENTS**：合并稳定工作规则、必要命令、文档入口；保留原有效规则，不保存进度、临时问题、
  聊天流水或测试日志，不全文复制本请求。工作区外层入口仅导航到源码根目录。
- **STATUS**：优先复用现有状态；不存在时建立 `docs/STATUS.md` 或根目录 STATUS。
  全项目只有一个权威入口；其他类似文档引用它，不删除用户内容，不重复维护进度。
  控制在约 100 行：时间、当前目标、完整需求/验收入口、可运行状态、进行中的工作、
  完成摘要及证据、最重要 1–3 个下一步、阻塞/风险/待确认、实际验证命令及结果、云端状态、恢复入口。
- **需求/计划**：多阶段任务或需求只在聊天中时，将完整范围、限制、交付物、顺序、里程碑和验收
  保存到已有合适文档；确有需要才新建。本文件承接此次要求，不另建空壳 PLAN。
  STATUS 只引用需求，不因精简而丢失需求，不写“继续上一条任务”作为替代。计划变化才更新此类文档。
- **决策/ADR**：仅有重要且长期有效的技术决策时记录背景、选择和原因，优先复用；无必要不创建。

首版状态来自实际代码、配置、文档、测试入口、GitHub 和明确任务，不能仅凭文件名推断。
工作状态区分“未开始 / 进行中 / 已实现但未验证 / 已完成且已验证”；云端状态另行区分
“尚未提交 GitHub / 云端提交成功且已核对 / 提交失败或受到阻塞”。
当前任务尚未完成必须标为进行中。历史验证和本次执行结果分开，未运行、失败、跳过如实记录；
文档配置、编译成功或提交成功不能代替实际功能验收。

新任务/压缩后先读 STATUS；按需读取需求和相关代码。平时在有意义步骤、关键验证、阻塞和阶段变化时
持续维护快照，主动压缩、交接、最终汇报前检查能否恢复。整理过时进度，保留必要完成摘要和证据入口，
历史交给 GitHub 提交记录。本次直接执行这些要求，不依赖新 AGENTS 是否被自动重新加载。

## 实施顺序与里程碑

1. 确认项目、基线、文档职责与远程状态，建立/增量更新规则、实际状态和必要需求。
2. 检查文档证据、相对路径、唯一状态入口及用户原工作保留情况；达到基础配置里程碑后直接进行可执行云端提交。
3. 若存在另一个明确业务任务，立即按原需求推进实现、相关检查与修复，达到功能或迁移/重构/测试检查点再提交。
   同一里程碑相关代码、测试、文档优先放在一次完整提交，不每保存一个文件就提交，也不全部拖到任务最后。
4. 汇总最终验证、云端核对、阻塞和恢复入口。真实阻塞如实报告，不宣称全部完成，不因完成配置而等待确认。

## 每次云端提交的执行门槛

依次完成：审阅实际文件差异并分离用户已有修改 → 执行阶段相关验证 → 更新 STATUS →
重读远程最新 HEAD/必要文件 → 比较开始基线、本次修改与远程变化 → 确认任务归属与文件范围 →
使用能说明目的的信息创建云端提交。

- 提交基于已经核对的最新远程树，完整保留本次范围外远程内容，不能用整个本地目录覆盖远程，
  不能把本地缺失文件当作删除请求。已有修改无法安全分离时暂缓该文件并记录原因，继续其他工作。
- 优先使用多文件原子接口与预期 HEAD 并发校验，例如 GraphQL `createCommitOnBranch` 的
  `expectedHeadOid`。REST Git Data API 如被使用，必须保留 base tree、显式父提交和非强制更新；
  发生竞争时重新检查相关文件，不能仅因引用更新允许快进就假定内容无冲突。
- 分支前进时重新读取、比较；无法保留并发修改则暂停相关写入，记录具体冲突。
  不强制更新分支、不改写历史、不删远程分支/标签、不绕过保护、签名或检查。
  目标分支不能直接写入时说明限制，不擅自合并别的分支；不创建其他仓库/Release、不改变可见性。
- 审查密钥、令牌、密码、私钥、未经授权公开的隐私、无关内容、依赖/构建/大型临时产物。
  不在输出或文档暴露敏感值。发现问题停止受影响提交，保留工作并说明处理需求，不擅自删用户文件或改历史。
- 工具部分成功时逐项核对实际结果，不把整批说成完成，不盲目重复提交。
- 提交后核对仓库确属 `EndiVee233/SubFabric`、预期分支已包含提交、文件和内容符合预期、
  范围外内容没有意外变化/删除。保留 SHA 与可访问提交链接；接口未报错本身不是充分成功证据。
- STATUS 仅记已发生并确认的结果。最终提交 SHA/核对可在最终报告补齐，
  不为把某次提交自身 SHA 写回 STATUS 反复提交；没有实质变化不刷新日期制造提交。
- 提交失败/认证缺失/工具不可用时记录原因、未提交内容与恢复入口，继续不受阻塞工作，
  不改成本地提交推送。不要求粘贴密码/令牌/私钥，只说明所需登录或权限配置，
  不擅自修改配置、关闭检查或绕过认证/签名限制。

## 限制与验收

不为 Markdown 配置查网络资料、安装依赖、引入框架或额外自动化；读取指定 GitHub 仓库、
核对远程与创建云端提交的必要网络访问在授权范围。业务操作仍遵循原任务授权与现有权限。
不创建、修改、启用或信任任何 Hook，不把调查 Hook 作为前置；未来确需使用须另提方案并明确确认。

验收覆盖：文档与实际证据一致；AGENTS 相对路径存在；权威状态唯一；完整需求未丢失；
原文件、已有修改、本地版本管理和远程范围外内容保留；仓库、分支、提交范围和实际结果均核对。
仅运行当前改动需要的现有检查。缺少依赖、服务、凭据、写权限等时，分别说明实现、验证与云端保存状态。

最终统一报告：新建/修改/复用文件；状态、完整需求与恢复入口；首版证据来源；原任务完成程度及实验/未完成项；
实际验证命令/结果及未运行/失败原因；实际仓库与分支；云端提交 SHA、说明、链接、范围及分支核对；
未提交内容及原因；用户与远程既有内容保留情况；剩余阻塞、待确认与下一步。
