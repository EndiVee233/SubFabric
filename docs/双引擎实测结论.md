# NPU + GPU 双引擎：实现与实测结论

> 写于 2026-10-08。这份文档记录**真实测到的数字**，包括对我不利的结果，
> 供后续判断这个功能值不值得继续投入。
>
> **⚠ 2026-10-11 复测：§三"没有收益"的结论已被推翻** —— 当前代码在当前机器上
> 双引擎比最快的单引擎再快 1.25 倍。**§五 是最新口径**，§二 / §三 只作为
> 当时那版代码的历史记录保留（先读 §5.2 再看它们，否则会被误导）。

## 一、实现了什么

| 文件 | 作用 |
|---|---|
| `asr/asr_dual.py` | 双引擎调度器：切片 → 同时喂两个引擎 → 按时间戳合并 |
| `asr/asr_npu.py` / `asr/asr.py` | 各加 `--manifest` 模式：**加载一次模型、批量跑多片** |
| `asr/asr_perf.py` | 性能测试：分阶段测出本机最佳配比（基线实测 + 推算 + 只验证最优） |
| `editor/server.js` | `parakeet-tdt-0.6b-v2-dual` 引擎条目、`asrEngineArgs` 分支、`/api/asr/dual` |
| `editor/index.html` + `js/project.js` | 识别模型页的分工下拉；设置页的「性能测试」标签页 |

设备约定（**两套编号含义相反，容易搞错**）：
```
OpenVINO:  GPU.0 = Intel Arc 核显      GPU.1 = NVIDIA RTX 4060
CUDA:      cuda:0 = NVIDIA RTX 4060
```
双引擎里 NPU 侧只碰 NPU + 核显（`--joint GPU.0`），N 卡整块留给 sherpa 侧，两边不抢同一块硬件。

## 二、实测结论（同一段 236 秒音频、8 秒分片）

```
只用 GPU（29 片）      18.4s = 12.8x 实时    每片 0.623s
只用 NPU（29 片）      25.6s =  9.2x 实时    每片 0.874s
两者并行 1:1（29 片）  33.9s =  7.0x 实时    GPU 每片 2.391s / NPU 每片 1.447s
前后半顺序跑（各一引擎）38.4s =  6.1x 实时
```

**并行时单个引擎会显著变慢**：GPU 每片 0.62s → 2.39s（慢 3.8 倍），NPU 0.87s → 1.45s（慢 1.7 倍）。
于是**并行（7.0x）比只用 GPU（12.8x）还慢 1.8 倍**。

同样配置重复跑的波动也很大：同一档 8s 分片实测出现过 7.0x / 14.3x / 19.8x 三种结果。

### 一个被我忽视的固定开销

顺序跑那组：NPU 识别本身只花 2.8s、GPU 只花 5.8s，但墙上时间 38.4s。
**大头是"启动 Python 进程 + 导入 OpenVINO / sherpa-onnx 运行时"**（每次 6~14s）。
我早期在**进程内**测的持续吞吐（21.9x / 16.1x）没有把这笔开销算进去，
所以与真实调用路径的数字对不上。

## 三、当时的结论（2026-10-08，**已被 §五 复测推翻，仅作历史记录**）

1. **双引擎在你这台机器上没有收益**。要用就只用「英语·快」（GPU 单引擎）——它是最快的单条路径。
2. `--ratio` 与分片长度这类"调优"在 2~3 倍的测量波动面前没有意义。
   分轮次调比例（`--round-sec`，默认 240s）机制本身工作正常，但基准太吵，调不出结论。
3. 动态队列的"每片起一次进程"版本实测只有 1.7x（每片重载模型），已移除；
   `--dynamic` 保留但标注不可用。

## 四、当时列出的待验证方向

**"并行导致单引擎变慢 3.8 倍"这个现象本身不寻常** —— 两个引擎理论上落在不同硬件上
（NPU+核显 vs N 卡），不该互相拖累这么多。可疑方向（都未验证）：

* 两者都要在 CPU 上做音频前处理（NumPy 加窗/归一化、OpenVINO 的预处理），**CPU 才是瓶颈**；
* 内存带宽竞争（sherpa int8 621MB + OpenVINO 2.4GB 模型常驻）；
* Windows 笔记本的功耗/散热墙：核显 + NPU + dGPU 同时满载会触发整机降频。

验证办法：跑并行时用任务管理器看 **CPU 占用是否打满**。若打满，说明是 CPU 瓶颈，
那双引擎的上限就是"单核处理音频的速度"，再怎么调比例都没用。

## 五、2026-10-11 复测：结论反转，以及"到底谁快、快在哪"

> 这一节是**当前最新口径**，§二 / §三 只作为历史记录保留。

### 5.1 三组真实调用路径对照

机器：Intel Core Ultra 7 155H（AI Boost NPU）+ Arc 核显 + RTX 4060 Laptop。
音频：600.0s（40s 英语样本重复 15 次，单声道 16k）。
分片：15.01s（= NPU 单窗口长度）→ 39 片。置信度档：`full`（= `--tta 2`，加噪重跑 2 遍）。
每组都走 `asr/asr_dual.py` 的**真实 spawn 路径**（不是进程内测速）：

| 配置 | 墙钟 | 实时倍率 | 每片（引擎自报） |
|---|---|---|---|
| `--ratio 0:1`（只用 NPU） | 50.8s | **11.8x** | 1.19 / 1.17 / 1.52 s |
| `--ratio 1:0`（只用 N 卡） | 47.5s | **12.6x** | 1.19 / 1.15 / 1.33 s |
| `--ratio 1:1`（双引擎） | 38.1s | **15.75x** | NPU 1.7~2.5s / N 卡 1.6~1.8s |

**所以：双引擎确实有意义，比最快的单引擎再快 1.25 倍。** 并行仍然让两边都变慢
（NPU 1.18→1.7~2.5s，N 卡 1.15→1.6~1.8s，与 §二 同向），但这次净收益是正的。

输出质量：三种配置跑出的**前 40 秒词序列逐词一致**（143/143 词；N 卡那条只有 4 处
标点/数字写法差异，如 `four` vs `4`），合并时间轴没有引入重复或错序。
同一段音频的 2185 词全量统计：NPU 2135 词 / N 卡 2139 词，覆盖到 600.0s / 600.0s。

### 5.2 为什么 §三 那版会得出"没有收益"

不是测量噪声，是**代码变了**：那版是 8 秒分片 + 每片重载模型的老路径，而且当时
NPU 侧的时间戳单位还是错的（40 秒音频的句子只覆盖到 28.9s，词间隔被压缩）。当前版本
单窗口 15.01s，时间戳覆盖整段。**结论有时效性，复测要重跑而不是引用。**

### 5.3 NPU 引擎的账：编码器很快，但整片不快

单窗口 15.01s（编码器=NPU，joint=GPU.0）拆开实测：

| 阶段 | 耗时 | 该片等效 |
|---|---|---|
| 编码器 `_encode`（NPU） | 0.142s | 105x 实时 |
| TDT 主循环 `_tdt_loop`（joint 在核显） | 0.137s | 111x 实时 |
| 干净解码一遍 `_decode_windows`（含两者） | 0.280s | 54x 实时 |
| **TTA 加噪重跑 ×2** | **0.641s** | —— |
| 模型加载（每进一次进程一次） | 3.1~3.5s | —— |
| 真实生产路径每片（含后处理） | ~1.0s | **14~15x** |

两个结论：

1. **NPU 的算力不是瓶颈**：编码器只占整片的 1/7；加噪两遍（0.641s）与"干净一遍"
   （0.280s）几乎等价，说明时间主要花在**逐帧串行的 TDT 主循环**上（joint 每帧一次
   微调用）。`full` 置信度档的稳定性重跑让每片成本变成约 3 倍 —— 这是当前 NPU
   引擎最大的单项开销。
2. **joint 放哪都不影响，而且现默认值就是最优**（TDT 主循环中位耗时）：

   | joint 设备 | TDT 主循环 | 说明 |
   |---|---|---|
   | `GPU.0`（Intel 核显） | **0.135s** | 当前默认，最快 |
   | `CPU` | 0.226s | 慢 1.7 倍 |
   | `GPU.1`（N 卡） | 0.353s | **慢 2.6 倍** |

   所以"把 joint 挪到独显"是错的：它跑几千次微调用，独显每次提交的开销吃掉了
   算力优势。`--joint GPU.0` 别按"独显更快"的直觉改。

### 5.4 已经改掉的：加噪重跑的编码器浪费（2026-10-11，本次）

**症状**：`full` 置信度档每片要跑三遍解码（干净 1 遍 + 加噪 2 遍），而**每一遍都完整
重跑了一次编码器** —— 编码器又是 NPU 上最贵的一步（单窗口 0.153s ≈ 整片的 1/6）。

**为什么这是纯浪费**：`_tdt_loop` 的噪声是加在**编码器输出**（acts）上的，不在编码器
输入上；同一份输入喂给 NPU，输出是**逐位确定**的。实测三遍的 acts `np.array_equal`
全为 True —— 后两遍算出来的东西和前一遍一模一样。

**改法**：`_decode_windows` 里加一层"编码结果按 (窗口偏移, 窗口长度) 缓存"，缓存生命周期
就是一次 `recognize_words`（进入时置空、跑完置回 None），所以不会跨音频串味。
**没有**去动窗口重叠合并那套逻辑（skip / emit_end / 最长后缀前缀去重）—— 试过把它整段
搬到"多遍一次性推完"的新实现里，结果多窗口输出与原来不同（35s 音频词表不一致、
60s 音频 217 vs 220 词），主路径不能拿这个赌，所以原逻辑逐字保留。

**实测（15.01s 分片、tta=2、同一段音频、同进程对拍 before/after）**：

| 项 | before | after | 结果 |
|---|---|---|---|
| 单窗口词表 | — | — | **逐字段相同** |
| 单窗口置信度 | 0.9090 | 0.9090 | **相同（含三个分量与稳定性统计）** |
| 单窗口耗时 | 1.003s | 0.737s | 1.36x |
| 多窗口 35s 词表 / 置信度 | 126 词 / 0.8880 | 126 词 / 0.8880 | **完全一致** |
| 多窗口 35s 耗时 | 2.573s | 1.757s | 1.46x |
| 多窗口 60s 词表 / 置信度 | 217 词 / 0.8850 | 217 词 / 0.8850 | **完全一致** |
| `recognize_words` 每片 | 0.870s（17.2x） | **0.626s（24.0x）** | **1.39x** |
| 编码器调用次数（单窗口 tta=2） | 3 | **1** | —— |

逐遍耗时也从 ~0.29s 掉到 ~0.15s（加噪那两遍不再编码，只剩 TDT 主循环）。
**稳定性指标的含义没有变**：噪声依旧加在 acts 上、种子依旧固定、受影响词数与
置信度分量逐位相同。

**真实 10 分钟路径复测**（600s 音频、15.01s 分片、full 档、`asr_dual.py` 真实 spawn）：

| 配置 | 优化前 | 优化后 | 提速 | 词数（前后） |
|---|---|---|---|---|
| 只用 NPU（`--ratio 0:1`） | 50.8s / 11.8x | **40.0s / 15.0x** | 1.27x | 2135 → 2139 |
| 双引擎 1:1 | 38.1s / 15.75x | **30.2s / 19.9x** | 1.26x | 2135 → 2135 |

副作用之一：**双引擎相对单引擎的优势从 1.25x 拉大到了 1.58x**
（30.2s vs 40.0s）—— 因为 NPU 侧的固定浪费被削掉后，两边的"净活"更接近，
并行分工的收益就更明显了。

### 5.5 已知但**没**改的东西（留给下一次）

* **三遍解码仍是串行的**。理论上可以重叠：编码器在 NPU 上跑时 joint 闲着，joint 跑时
  NPU 闲着。但尝试两条路都受阻：
  ① 线程并发 —— `InferRequest` 非线程安全（`RuntimeError: Infer Request is busy`），
     即使每遍各建一套请求，共享的 recognizer 仍会把请求换掉；
  ② OpenVINO 异步提交（`start_async` + `wait`）把三遍编码排队 —— 实测**更慢**
     （0.597s vs 串行 0.427s），NPU 队列并不会让同一设备的多次提交真并行。
  剩下真正可行的是"先把所有遍的编码做完，再逐遍跑 TDT"的两段式，但那要求把窗口重叠
  合并逻辑也按遍复制一遍（见 5.4 的教训），需要更小心的等价性验证，本次没做。
* `_tdt_loop` 每帧都 `np.asarray(logits_all).reshape(-1, 1030)`，把 188 帧 × 1030 的
  输出整体复制一遍（`collect_probs` 时还对每行算一次 softmax），而每次只用其中一行。
  实测单次 joint 只要 0.001s、188 次累计约 0.19s，**剩下的 ~0.17s/遍是 Python 与
  NumPy 的每帧固定开销** —— 这块比 joint 本身更值得优化。
* 双引擎没有走常驻识别服务（`editor/asr-service.js`），每次调用重载两套模型
  （NPU 3.5s + sherpa 4.8s）。短音频不划算就是这个原因。
